MCPs Unity e Blender — notas de teste (2026-11-09)

Blender (blender-mcp via uvx) — carregou; socket NÃO conectou

Ferramentas: get_addon_status, get_scene_info, execute_blender_code, look, search_assets, import_asset, generate_3d (gasta crédito, não usar), record_trajectory_feedback, disable_telemetry. Erro nas chamadas: "Could not connect to Blender. Make sure the Blender addon is running." → falta o criador clicar Connect no painel BlenderMCP. Trabalho feito em headless: D:\Blender\blender.exe -b -P tools/blender/mannequin_base.py -- saida.glb (Blender 5.2.3).

Resolvido em 2026-11-10 — conectado (porta 9876, protocolo 15)

Causa: o app do Claude é empacotado (MSIX) e o que ele grava em %APPDATA% é redirecionado; o Blender da interface não enxergava scripts/addons/blender_mcp_addon.py (o headless lançado pelo Claude enxergava, por isso parecia instalado). Correção: cópia do addon em tools/blender/addons/ e, no console Python do Blender: bpy.ops.preferences.addon_install(filepath=r'[removido]', overwrite=True); addon_utils.enable('blender_mcp_addon', default_set=True); bpy.ops.wm.save_userpref(); bpy.ops.blendermcp.start_server() A cada abertura do Blender: aba lateral (N) MCP for Blender → Start/Connect. Regra geral: nunca instalar nada para outros programas gravando em %APPDATA% pelo Claude; usar uma pasta em D:\ e deixar o próprio programa instalar.

Unity MCP (unity mcp --project-path ...) — CONNECTION_CLOSED (corrigido em 2026-11-10)

Causa (log %LOCALAPPDATA%\claude-cli-nodejs\Cache\D--Jogos-ragnatale\mcp-logs-unity\.jsonl): o command era o caminho do alias com espaço ([removido] Pio\...\unity.exe); o Claude Code o repartiu no espaço e a CLI recebeu "comando desconhecido 'Pio\AppData\...\unity.exe'" e saiu. O servidor em si está ok (testado à mão: initialize responde com alias ou caminho real; sem Editor, tools/list devolve só unity-cli-status, "nenhuma instância do Pipeline"). Correção: .mcp.json com "command": "unity" (alias no PATH, sem espaço). Reiniciar a sessão do Claude para o MCP carregar; as ferramentas do Editor só aparecem com o Editor aberto (tools/listChanged). Antes da correção, nenhuma ferramenta mcp__unity__ aparecia na sessão. Contorno que funciona: o Unity CLI fala com o Editor aberto (Pipeline, porta 7800, unity status = ready): unity command <grupo> <comando> --no-banner (listar: unity command). Grupos úteis: console, scene, capture, component, gameobject, lighting, asset, package, test, script eval (roda C# no Editor), editor. Testado:

  • Console: console get --level warn --tail 5 / console clear — OK.
  • Cena aberta: scene list_open, scene get_hierarchy — OK (hierarquia grande; filtrar com grep).
  • Captura: capture game_view --output-path ... devolve PNG (source=screen/camera, até 4096) — OK. Para 1920x1080 determinístico usamos M1Capture.RunB (RenderTexture).
  • Testes: test run --mode editor — 10/10 passam com o Editor aberto (batchmode bloquearia o projeto).
  • Pacotes: package add --name X --confirm --wait.

Pegadinhas: durante recompilação/domain reload o CLI diz "no editor"; esperar unity status = ready.

Pacote adicionado

com.unity.cloud.gltfast 6.20.0 (importa .glb; o Unity 6.6 não importa glTF nativamente).

Abrir o Unity Editor pelo Claude sem perder a licença (2026-11-10)

Processo filho do app do Claude (MSIX) enxerga um %LOCALAPPDATA% redirecionado, sem o token do Hub → "No valid Unity Editor license found". Abrir por fora do container: explorer.exe [removido] (o Explorer lança o Editor como processo comum, que acha a licença). Nunca chamar Unity.exe direto do Claude.

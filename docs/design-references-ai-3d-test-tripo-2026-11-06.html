Lição de ordem do pipeline (Tripo)

Gerar (triângulos) -> segmentar -> retopologizar (quad) -> esqueleto. Retopologizar antes impede a segmentação.

Lições dos erros (como o Tripo funciona), para o script de produção

  1. Ordem importa: gerar (triângulos) → segmentar → retopologizar (quad) → esqueleto. Quad não aceita segmentação.
  2. Restaurar versão pelo histórico demora alguns segundos para refletir; não clicar de novo.
  3. Preço riscado ("40 → 0") na interface = tentativa grátis do pacote de boas-vindas.
  4. Cada operação cria uma nova versão do modelo; o histórico guarda só 1 dia no plano grátis (baixar o que importar).
  5. API: a URL do modelo expira em 5 minutos (baixar na hora); export_orientation não deve ser definido se houver pós-processamento (converter no fim).
  6. Plano grátis: o modelo fica público e a Tripo fica com os direitos; só avaliação.
  7. Esqueleto exige malha leve (limite de polígonos): fluxo completo = gerar -> segmentar -> retopologizar (triângulo, até 20k) -> auto rig. Para a malha final em quads, retopologizar quad por último (sem segmentar de novo).
  8. Saldo grátis do Studio: 200 créditos = geração 55 + retopo quad 40 + retopo triângulo 35 = 130 gastos; sobram ~70 (rig 20).

Resultado do pipeline completo (grátis, conta Studio)

Gerar (55) -> segmentar (grátis x1, 15 partes) -> retopo triângulo 20k (35) -> auto rig Mixamo (20) = funcionou de ponta a ponta. Saldo final: 50 de 200 créditos. Falta: exportar GLB (pode exigir plano pago) e avaliar no Blender. Nota provisória: ~70/100. Pontos fracos: peso/ordem das etapas (segmentar antes de retopologizar quad), malha final triangulada ~21k (acima do alvo de 10k), exportação não testada.

Atualização: exportação

O Studio grátis não exporta. O caminho viável para o jogo é a API com créditos pagos (multiview-to-model -> segmentar -> retopologia -> rig, baixando o GLB na hora). Um modelo gerado no Studio grátis não pode ser baixado nem usado.

Teste 2: API paga, conceito v2 oficial (3 vistas), P2-20260801, quad, face_limit 20000

  • Custo real: 120 créditos (US$ 1,20); saldo 500 -> 380. Arquivo: assets/external/tripo/output/warrior_t1_p2.fbx (8,9 MB; quad força FBX).
  • eval_model.py: 1 objeto de malha (não dividido), 0 ossos, 23.899 polígonos (41.070 triângulos, 72% quads), 1 material, UV ok, altura 0,892 m (escala a ajustar).
  • Visual: muito mais próximo do conceito v2 (elmo com crista e viseira, ombreiras, cota, tabardo azul, escudo de runas nas costas, espada, botas). Fiel nas 3 vistas.
  • Defeitos: ~8 fragmentos soltos flutuando (tiras/placas), parte inferior do tabardo semitransparente, orientação do modelo girada 90° (vem olhando para +X), tudo numa malha só.
  • A série P não suporta generate_parts/segmentação; quad não segmenta. Para dividir em peças: gerar na série H (triângulos) com generate_parts ou segmentar via API, e só depois retopologizar cada parte.

Teste 3: dividido em partes (série H v3.1 + smartsegment modelo, granularidade média)

  • Custo real: 95 créditos (US$ 0,95); saldo 285. Arquivo: warrior_t1_h_parts.glb (8,4 MB), fora do git.
  • Avaliação no Blender (eval_model.py): 8 malhas (tripo_part_0..7), 58.716 triângulos no total (17.213 / 11.340 / 10.582 / 5.762 / 4.226 / 3.522 / 4.162 / 1.909), 8 materiais, UV em todas, 0 ossos, sem quads.
  • Etiquetas da segmentação: helmet, armor, tunic, belt, sword, leg armor, boots.
  • O erro de MemoryError anterior foi intermitente (o arquivo está íntegro); o EEVEE do Blender falhou 1x em render e passou na repetição.
  • Visual: mantém a fidelidade ao v2 realista e agora separado em peças. Total 58k triângulos é ~3x o orçamento de herói (10-15k): precisa de retopologia por parte.
  • Decisão de estilo em aberto: o v2 é realista e sombrio; o criador prefere linguagem mais próxima do Priston (estilizado, ornamentado, saturado). Conceitos A/C gerados para escolher (assets/concepts/warrior/warrior_sheet_v3A/C.png).

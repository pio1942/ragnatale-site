ADR-0004: Formato de dados, ids estáveis e versionamento

Status

Accepted (2026-11-08) — confirmação explícita do criador, dada por ele mesmo no chat: "1 - aprovado", em resposta ao pedido "aceito as ADRs 0002 a 0008".

Date

2026-11-07

Last Verified

2026-11-07 (contra scripts/data/*.gd, data/ e docs/engine-reference/godot/current-best-practices.md seção Resources)

Decision Makers

technical-director (proposta), lead-programmer

Summary

Conteúdo (classes, monstros, itens, habilidades, quests) é definido hoje por Resources .tres com id igual ao nome do arquivo e lido por DataDB. Com o jogo online e o conteúdo crescendo (166 NPCs, 23 mapas, centenas de itens), é preciso fixar regras de id, versionamento e carga para que servidor, cliente e personagens salvos concordem.

Context

Problem Statement

CLAUDE.md fixa "id estável = nome do arquivo", mas não há regras para renomear, aposentar, versionar nem validar. Registros salvos e telemetria dependem desses ids (TR-anticheat-007: todo def_id precisa existir em DataDB).

Requirements

TR-monsters-001, TR-items-001, TR-classes-001, TR-balance-001, TR-quests-001, TR-skills-001

Decision

  1. Definição de conteúdo = Resource tipado em data/<tipo>/<id>.tres; id = nome do arquivo, snake_case, imutável após publicado. Renomear = criar novo id e marcar o antigo retired com replaced_by.
  2. Todo Def tem schema_version. DataDB valida na carga (campos obrigatórios, faixas, referências cruzadas) e falha alto no servidor; o teste unitário valida o conteúdo inteiro.
  3. Hash de conteúdo (content_hash) calculado na carga e enviado no Hello do protocolo; cliente com hash diferente é recusado.
  4. Balanceamento global continua em scripts/sim/balance.gd (constantes), valores por entidade em .tres; nenhum valor de jogo no código de regra.
  5. ItemInstance e estado de personagem referenciam apenas ids, nunca Resources embutidos (ver ADR-0002).
  6. Clonagem de Defs em runtime usa duplicate_deep(); Defs são tratados como somente leitura em runtime.
  7. Dados grandes (bestiário, NPCs) permanecem em .tres; geração por script a partir de tabelas só gera .tres (nunca lido direto em runtime).

Alternatives Considered

AlternativaPor que não
JSON/CSV lidos em runtimeperde tipagem e a validação do editor
Banco de conteúdo no servidorcliente precisa do mesmo conteúdo; complexidade sem ganho no MVP
Ids numéricosilegíveis em logs e em telemetria

Consequences

Positivas: sem divergência cliente-servidor, conteúdo revisável por diff. Negativas: aposentar id exige disciplina; carga de milhares de .tres pode alongar o início do servidor.

Performance Implications

  • Carga de DataDB no início do servidor: meta menor que 2 s para o conteúdo do MVP (a medir).
  • Memória do conteúdo no cliente dentro do teto de 2048 MB (project.yaml).

Validation Criteria

  • Teste que percorre todos os .tres e valida esquema, faixas e referências.
  • Teste de handshake com content_hash diferente recusado.
